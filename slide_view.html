01 · KONSEP & ARSITEKTUR Tabel Virtual vs Tabel Fisik

Apa itu Database View?

View adalah tabel virtual (logical table) yang didasarkan pada hasil kueri SQL. View tidak menyimpan rekaman data fisik tersendiri di disk, melainkan menyimpan definisi kueri di kamus data (data dictionary).

PRINSIP Mekanisme Kerja Virtualisasi

Saat aplikasi mengeksekusi SELECT * FROM nama_view, MySQL Query Engine secara dinamis menjalankan kueri pembentuknya ke tabel-tabel fisik dasar di bawahnya.

  • Nol Redundansi Penyimpanan: Menghemat media penyimpanan fisik disk.
  • Dynamic Result Set: Selalu merefleksikan perubahan terkini dari tabel fisik dasar secara langsung.
  • Interface Transparan: Pengguna berinteraksi dengan View persis seperti tabel fisik biasa.

02 · MANFAAT & TUJUAN Nilai Bisnis & Rekayasa Perangkat Lunak

4 Alasan Strategis Menggunakan View

Penerapan View dalam sistem basis data perusahaan bukan sekadar alternatif sintaks, melainkan pilar penting keamanan, konsistensi data, dan arsitektur modular:

01 Keamanan & Masking

Menyembunyikan baris atau kolom sensitif (seperti kolom password kasir atau kontak pribadi customer) tanpa memodifikasi struktur tabel fisik aslinya.

02 Simplifikasi Kueri

Kueri kompleks yang menggabungkan 5 tabel (INNER JOIN), filter tanggal, dan kalkulasi subtotal dibungkus rapi sehingga pemrogram klien cukup memanggil 1 kueri simpel.

03 Konsistensi Rumus

Menjamin rumus bisnis terpusat (contoh: banyak * hargajual). Mencegah disparitas formula antarmuka di berbagai aplikasi kasir / backend.

04 Independensi Data

Jika tabel fisik dipecah atau dinormalisasi ulang di masa depan, antarmuka kolom View dapat dipertahankan agar kode program klien tidak mengalami kerusakan (*breaking changes*).

03 · SINTAKS DEKLARASI MySQL 8.0 Reference Standard

Anatomi Sintaks CREATE VIEW di MySQL

MySQL menyediakan kontrol deklaratif penuh mulai dari algoritma eksekusi, pemilik hak akses (definer/invoker), hingga proteksi integritas:

FORMAL SINTAKS DDL
CREATE [OR REPLACE] [ALGORITHM = {UNDEFINED | MERGE | TEMPTABLE}] [DEFINER = user] [SQL SECURITY { DEFINER | INVOKER }] VIEW view_name [(column_list)] AS select_statement [WITH [CASCADED | LOCAL] CHECK OPTION];
CONTOH KASUS: VIEW KATALOG HARGA
-- Membuat view display produk aktif CREATE OR REPLACE VIEW vw_KatalogAktif AS SELECT kodeproduk AS kode, UPPER(namaproduk) AS produk, harga, stok FROM produk WHERE stok > 0; -- Memanggil data dari view SELECT * FROM vw_KatalogAktif ORDER BY harga DESC;

04 · KLASIFIKASI TEKNIS Simple View vs Complex View

Klasifikasi: Simple View vs Complex View

Pemahaman perbedaan mendasar antara kedua jenis View ini menentukan apakah data pada tabel fisik dapat diperbarui secara langsung melalui View tersebut:

Parameter Pembanding Simple View Complex View
Tabel Sumber Data Hanya berasal dari 1 tabel fisik dasar (single table). Menggabungkan 2 tabel fisik atau lebih melalui relasi JOIN.
Fungsi Agregasi Tidak mengandung fungsi agregat (SUM, AVG, COUNT, MIN, MAX). Sering menggunakan fungsi kalkulasi agregasi dan statistika.
Pengelompokan Baris Tidak menggunakan klausul GROUP BY atau HAVING. Menggunakan GROUP BY dan filter HAVING untuk ringkasan.
Penyaringan Duplikasi Tidak menggunakan klausa DISTINCT. Bisa menggunakan DISTINCT atau operator UNION.
Pemetaan Kolom Setiap kolom memetakan 1-ke-1 langsung ke kolom tabel fisik. Mengandung ekspresi kalkulasi (contoh: banyak * hargajual).
Kemampuan DML Updatable (Dapat di-INSERT, UPDATE, DELETE). Read-Only (Sebagian besar hanya dapat dibaca).

05 · DML PADA VIEW Aturan Deterministik MySQL

Syarat Mutlak Updatable Views di MySQL

MySQL mengizinkan operasi DML (INSERT, UPDATE, DELETE) pada View jika baris View memiliki korespondensi 1-ke-1 yang jelas dengan baris fisik di bawahnya:

ATURAN Kriteria Larangan DML (Non-Updatable)
  • Tidak mengandung fungsi agregat: SUM, COUNT, AVG, MIN, MAX.
  • Tidak menggunakan klausa DISTINCT atau UNION.
  • Tidak mengandung GROUP BY atau HAVING.
  • Kolom yang dimodifikasi bukan kolom hasil ekspresi kalkulasi aritmatika.
  • Tidak terdapat subquery di dalam SELECT-list atau klausa FROM target.
  • Algoritma harus MERGE (bukan TEMPTABLE).
  • Untuk operasi INSERT: Semua kolom NOT NULL tanpa default value pada tabel fisik wajib disertakan pada definisi View.
CONTOH: UPDATE STOK VIA VIEW
-- 1. View Updatable untuk Staf Gudang CREATE OR REPLACE VIEW vw_UpdateStokGudang AS SELECT kodeproduk, namaproduk, stok FROM produk; -- 2. Melakukan UPDATE stok melalui View UPDATE vw_UpdateStokGudang SET stok = 25 WHERE kodeproduk = 'P001'; -- 3. Verifikasi: Data pada tabel fisik PRODUK ikut berubah! SELECT * FROM produk WHERE kodeproduk = 'P001';

06 · KONTROL INTEGRITAS Mencegah Anomali Phantom Update

Proteksi Integritas: WITH CHECK OPTION

Tanpa klausa pelindung, pengguna dapat memasukkan data yang melanggar filter WHERE. Data berhasil masuk ke tabel dasar, namun langsung "hilang" dari tampilan View:

ANOMALI Masalah Tanpa CHECK OPTION

Jika sebuah View dibuat dengan syarat WHERE harga >= 5000 tanpa klausul CHECK OPTION:

UPDATE vw_ProdukMahal SET harga = 2000 WHERE kodeproduk = 'P004';

⚠ Kueri berhasil! Namun harga P004 sekarang 2000, sehingga produk tersebut seketika hilang dari hasil SELECT view tersebut.

SOLUSI Penyematan WITH CHECK OPTION
CREATE OR REPLACE VIEW vw_ProdukPremium AS SELECT kodeproduk, namaproduk, harga, stok FROM produk WHERE harga >= 5000 WITH CHECK OPTION;
Simulasi Respon Database:
ERROR 1369 (HY000): CHECK OPTION failed 'minimarket.vw_ProdukPremium'

07 · HIERARKI BERTINGKAT Perilaku Validasi pada Nested Views

Evaluasi Hierarki: LOCAL vs CASCADED

Ketika sebuah View dibuat di atas View lain (View on top of View), MySQL menyediakan dua cakupan pengujian integritas kondisi klausa WHERE:

OPSI 1 WITH LOCAL CHECK OPTION

Hanya memvalidasi kondisi WHERE dari View itu sendiri. Kondisi View di bawahnya HANYA diuji jika View di bawahnya tersebut secara eksplisit memiliki klausa CHECK OPTION.

Eksperimen Kasus: Mengubah alamat customer Yogyakarta menjadi 'Sleman' melalui View Anak berstatus LOCAL: BERHASIL (karena View Induk tidak memiliki check option).
OPSI 2 (DEFAULT) WITH CASCADED CHECK OPTION

Menguji kondisi WHERE dirinya DAN seluruh rantai View di bawahnya secara rekursif, meskipun View di bawahnya TIDAK mendeklarasikan check option.

Eksperimen Kasus: Mengubah alamat menjadi 'Sleman' melalui View Anak berstatus CASCADED: DITOLAK (Error 1369) karena melanggar syarat View Induk.

08 · INTERNAL ENGINE Optimasi Eksekusi & Hak Akses Pengguna

Algoritma Pemrosesan & Hak Akses Keamanan

Mengontrol bagaimana database engine mengeksekusi kueri View secara internal serta hak akses kredensial mana yang digunakan:

ALGORITHM Strategi Query Optimizer
  • MERGE: Kueri pemanggil digabungkan langsung dengan kueri definisi View. Indeks tabel fisik dapat dimanfaatkan penuh dan mendukung Updatable View.
  • TEMPTABLE: Hasil View dimaterialisasi ke tabel sementara di memori/disk terlebih dahulu. Indeks tabel fisik tidak terbawa, lebih lambat, dan selalu Read-Only.
  • UNDEFINED (Default): Optimizer otomatis memilih MERGE bila memungkinkan, atau beralih ke TEMPTABLE jika ada agregasi/GROUP BY.
SECURITY Konteks Otorisasi (DEFINER vs INVOKER)
  • SQL SECURITY DEFINER (Default): View dieksekusi dengan izin akun pembuat/definer. Pengguna pemanggil hanya butuh izin SELECT pada View tanpa perlu akses ke tabel fisik. Sangat aman untuk menyembunyikan tabel master kasir.
  • SQL SECURITY INVOKER: View dieksekusi dengan izin akun pengguna yang sedang login. Pengguna wajib memiliki izin SELECT pada View DAN seluruh tabel fisik terkait.

11 · KUNCI SOLUSI Pedoman Khusus Dosen & Asisten Praktikum

Kunci Jawaban & Analisis Teknis

Pilihlah nomor soal untuk melihat kueri SQL DDL/DML solusi baku dan analisis logis database engine:

SOLUSI SQL: SOAL 1
CREATE OR REPLACE VIEW vw_KatalogProdukAktif AS SELECT kodeproduk, UPPER(namaproduk) AS nama_produk_kapital, harga, stok, CASE WHEN stok = 0 THEN 'Stok Habis' WHEN stok < 10 THEN 'Stok Kritis' ELSE 'Stok Aman' END AS status_stok FROM produk; -- Kueri Pengujian: SELECT * FROM vw_KatalogProdukAktif ORDER BY nama_produk_kapital ASC;
ANALISIS Penjelasan Logika & Output

Kueri memanfaatkan fungsi bawaan UPPER() untuk standarisasi huruf kapital dan struktur kendali CASE-WHEN untuk mengevaluasi ambang batas unit stok. View ini bersifat read-only untuk kolom kalkulasi status_stok, namun jika dialgoritmakan MERGE, kolom harga dan stok tabel dasar tetap dapat diakses.
